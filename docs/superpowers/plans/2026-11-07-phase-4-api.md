# Phase 4: Thin API, SSE and the queue-driven worker — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The React frontend talks to a real FastAPI service: chats, paged messages, idempotent submit, request detail with usage, cancel, inline replies and a live SSE timeline, while an in-process worker consumes the queue and runs each request through phase 1's `RequestRunner`.

**Architecture:** `api` is a thin HTTP layer: a route validates the wire shape, resolves the dev user and the owned chat, calls one service function and returns the entity it gets back. Every rule (ownership, idempotency scope, the cancel transition, reply verification, paging, the SSE event diff) lives in `core/services` and is tested without HTTP. `api/deps.py` is the composition root: one `Repositories`, `BlobStore` and `Queue` shared by the routes and the worker. The worker is a `QueueConsumer` on a background thread started by the app lifespan (behind `CONTEXTFORGE_RUN_WORKER_IN_API`); it calls `RequestRunner.start` or `RequestRunner.resume_claimed` over a SQLite checkpointer. SSE polls the repositories (the request, its Tasks, its assistant Messages) and sends whole records whose content changed.

**Tech Stack:** Python 3.12, FastAPI, sse-starlette, pydantic-settings, uvicorn, httpx (for `TestClient`), and phase 1's stack: LangGraph with `langgraph-checkpoint-sqlite`, Pydantic 2, `python-ulid`, pytest, ruff, mypy strict.

**Spec:** `docs/implementation-plan.md` sections 3.3 (who writes what), 6 (lifecycles), 7.5 (conditional writes), 11.1 to 11.6 (endpoints E1 to E16, payloads, SSE contract) and 12 (layout, rules, 12.1 naming); `docs/system-design.md` section 14 row "4 Thin API and UI" and section 15 (who decides); `.superpowers/milestone-2/brief.md` for the wave decisions. The frontend contract is `context-forge-frontend/src/api/httpClient.ts` and `types.ts`. Read them before any task.

## Global Constraints

- Python 3.12; `uv` with a committed `uv.lock`; `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .` and `uv run mypy src` all clean before every commit.
- Layering (spec 12): `core` imports nothing of ours; `api` and `worker` import `core`. Inside `api`, only `api/deps.py` and `api/app.py` import `worker` (the composition root has to build it).
- "Routes call services; services hold the rules and are tested without HTTP" (spec 12). A route body is: parse, one service call, return.
- "The API types are the Pydantic entities from section 3 with storage keys stripped; there is no second schema layer" (spec 11). Routes return entities; `api/schemas.py` holds request bodies only, built on the same `Entity` base (camelCase aliases, `extra="forbid"`).
- JSON, camelCase, ISO 8601 UTC timestamps, ULID ids (11.2). Enum values and error codes exactly as the spec writes them.
- One error shape everywhere: `{ "error": { "code": "...", "message": "..." } }`. Codes: `validation` 400, `unauthenticated` 401, `not_found` 404, `invalid_state` 409, `not_pending` 409, `payload_too_large` 413, `upload_mismatch` 422. Messages are user-facing; no stack traces (11.2).
- "A chat the caller does not own returns 404, never 403" (11.2).
- List endpoints take `limit` and `cursor` and return `{ "items": [...], "nextCursor": "..." | null }`; the cursor is opaque (11.2).
- "Writes that start or resume work return the Message they created" (11.2).
- Who writes what (3.3, 11.3, 11.4): the API writes request, clarification_response and action_response Messages, sets CANCELLED, and on a reply moves the request WAITING_USER to RUNNING; the worker writes clarification, proposed_action, report and text and owns every other status.
- Identity comes from the session, never from a body field (11). Phase 4's session is a dev login: the fixed `CONTEXTFORGE_DEV_USER_ID`.
- SSE (11.5): events `request`, `task`, `message`, each carrying the whole record; a `: heartbeat` comment every 15 seconds; the handler polls the repositories once per second (`sse_poll_ms: 1000`); the server closes after the `request` event carrying COMPLETED, FAILED, CANCELLED or WAITING_USER; a request already closed when the stream opens gets that one `request` event. SSE and the API read Messages and Tasks only; nothing in `RequestState` is shown.
- Queue: in dev the `InProcessQueue`, consumed by one background thread inside the API process; the SQS adapter arrives in phase 10 behind the same `Queue` Protocol. The checkpointer is `SqliteSaver` at `settings.checkpoint_path`.
- CORS allows the Vite dev origin `http://localhost:5173` (and `http://127.0.0.1:5173`).
- Every API log line carries `http_request_id`; `X-Request-ID` is accepted and echoed.
- No network, no AWS and no paid model in tests: the scripted model and in-memory repositories only.
- Tests: few, clubbed, integration-focused, one module per task. Functions about 40 lines at most; no duplicated logic blocks.
- Shared files this plan touches, additively: `pyproject.toml`, `worker/deps.py`, `tests/helpers.py` (plus one private helper's first parameter, Task 3), `tests/conftest.py`, `.env.example`, `.gitignore`, `docs/progress.md`. Phase 1 modules it extends: `core/logging.py`, `core/repositories/{base,memory}.py`, `core/services/submit.py`, `worker/runner.py`.

## Review Focus

1. The worker writes WAITING_USER before the clarification Message (phase 1 fix `8d959ff`): a stream polling between those two writes must not close on a question the client cannot see yet; it closes only once an unanswered clarification or proposed_action of the request is visible (Task 7).
2. A double-clicked answer: two replies to the same clarification must store one clarification_response and queue one resume; the second gets 409 `not_pending` (Task 4).
3. A run that raises something unexpected (a storage error, a bug): the worker thread must survive, the request must end FAILED with a user-facing reason that contains no exception text, and the next queued request must still run (Task 6).
4. A Task or Message changed twice within one second (`updatedAt` has second precision): the stream must still send the later state, so "changed" is decided by the record's content, not its timestamp (Task 7).
5. One `Idempotency-Key` value reused in another chat: it must create a new request there, never return a Message from a different chat (Task 3).

- Produces:
  - `paging.Page[T](Entity)`: `items: list[T]`, `next_cursor: str | None` (wire `{items, nextCursor}`).
  - `paging.page_descending[T](items: Iterable[T], *, key: Callable[[T], tuple[str, ...]], limit: int, cursor: str | None) -> Page[T]`: sorts by `key` descending, keeps the items whose key is strictly below the cursor's key, returns the first `limit`; `next_cursor` is the last returned item's key as URL-safe base64 of its JSON list when more items remain, else None. A cursor that fails any step of decoding (base64, UTF-8, JSON, not a list of strings) raises `ValidationFailed("Invalid cursor")`. Phase 10 swaps the slicing for DynamoDB's `LastEvaluatedKey` behind the same return type.
  - `chats.TITLE_MAX_CHARS = 60`; `chats.title_from_request(content: str) -> str`: whitespace runs collapse to one space, ends stripped; longer than 60 characters becomes the first 59, right-stripped, plus `…` (the frontend mock's rule).
  - `chats.create_chat(repos: Repositories, *, user_id: str, title: str | None) -> Chat`: ACTIVE, new ULID, `title` `""` when None.
  - `chats.owned_chat(repos, *, user_id: str, chat_id: str) -> Chat`: `NotFound("Chat not found")` when the chat is missing, belongs to another user (the repository is keyed by user, so it is simply missing) or is ARCHIVED.
  - `chats.list_chats(repos, *, user_id: str, limit: int, cursor: str | None) -> Page[Chat]`: ACTIVE chats, key `(updated_at, chat_id)`.
  - `chats.list_messages(repos, chat: Chat, *, limit: int, cursor: str | None) -> Page[Message]`: pages by `(message_id,)` from the newest; each page's items are returned oldest first (the 11.4 example order).
  - `chats.touch_chat(repos, chat: Chat, *, title: str | None = None) -> Chat`: saves the chat with `updated_at = now_iso()` and `title` when given; returns it. `chats.rename_chat(repos, chat: Chat, title: str) -> Chat` is `touch_chat` with the title. `chats.archive_chat(repos, chat: Chat) -> None` saves status ARCHIVED.
  - `auth.owned_chat_dep(chat_id: str, user_id: UserIdDep, container: ContainerDep) -> Chat`; `OwnedChatDep = Annotated[Chat, Depends(owned_chat_dep)]`. Every chat-scoped route takes `chat: OwnedChatDep`.
  - `schemas.CreateChatBody(Entity)`: `title: Annotated[str, StringConstraints(strip_whitespace=True, max_length=200)] | None = None`. `schemas.RenameChatBody(Entity)`: `title: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=200)]`. `schemas.Limit = Annotated[int, Query(ge=1, le=100)]` (routes default it to 50); `schemas.Cursor = Annotated[str | None, Query()]`.
  - Routes: `POST /chats` (body optional; the frontend sends `{}`) → 201 `Chat`; `GET /chats?limit&cursor` → 200 `Page[Chat]`; `PATCH /chats/{chat_id}` → 200 `Chat`; `DELETE /chats/{chat_id}` → 204; `GET /chats/{chat_id}/messages?limit&cursor` → 200 `Page[Message]`.

- Produces:
  - `events.Snapshot` frozen dataclass: `request: RequestMessage`, `tasks: list[Task]`, `messages: list[Message]` (the request's assistant Messages, `message_id` order), `pending: bool` (an unanswered clarification or proposed_action of the request exists).
  - `events.read_snapshot(repos: Repositories, chat_id: str, message_id: str) -> Snapshot`: reads the request first, then its Tasks, Messages and pending entries.   - `events.StreamEvent` frozen dataclass: `event: Literal["request", "task", "message"]`, `data: str` (the whole record, `model_dump_json(by_alias=True)`), `id: str` (the newest `updatedAt` this stream has sent so far: the resume mark).
  - `events.EventTracker(*, since: str | None = None)` with property `closed: bool` and `poll(self, snapshot: Snapshot) -> list[StreamEvent]`:
    - A request is closing when its status is COMPLETED, FAILED or CANCELLED, or WAITING_USER with `snapshot.pending` (the worker writes WAITING_USER before the question).
    - The first poll of a closing request returns exactly one `request` event and closes (11.5: one code path for the client).
    - Otherwise it returns one event per Task (`task_id` order), then per Message, then the request, for each record whose JSON differs from what this stream last sent for that id; content decides, not `updatedAt`. On the first poll, when `since` is given, records with `updated_at < since` are remembered without being sent (the client had them).
    - When the request is closing, the last event is the `request` event (appended even if unchanged) and the tracker closes.
  - Route `GET /chats/{chat_id}/requests/{message_id}/events` with `last_event_id: Annotated[str | None, Header()] = None`: calls `owned_request` before streaming (404 envelope, never an empty stream), then returns `EventSourceResponse(stream, ping=settings.sse_heartbeat_seconds, ping_message_factory=lambda: ServerSentEvent(comment="heartbeat"), sep="\n")`. The `stream` async generator: `tracker = EventTracker(since=last_event_id)`; each loop reads `await run_in_threadpool(read_snapshot, repos, chat_id, message_id)` (repository reads block; phase 10's are network calls), yields `ServerSentEvent(data=e.data, event=e.event, id=e.id)` per event, returns when `tracker.closed` or after `settings.sse_max_seconds` (a dead worker never holds a connection; the client reconnects), else sleeps `settings.sse_poll_ms / 1000`.
  - `tests/api_support.sse_events(body: str) -> list[dict[str, str]]`: splits the body on blank lines and returns each block's `event`, `data` and `id` fields; comment-only blocks (heartbeats) are dropped.
  - `tests/conftest.py`: an autouse fixture that sets `sse_starlette.sse.AppStatus.should_exit_event = None` when the attribute exists (sse-starlette binds one exit event to the first event loop it sees; every `TestClient` runs its own loop).

import json
from pathlib import Path
from typing import Any

def _model(*plans: dict[str, Any]) -> ScriptedModel:
    return ScriptedModel({"plan": [ModelResponse(structured=p) for p in plans],
                          "execute": [ModelResponse(structured=t1_result())] * 3})


def _chat(client: TestClient, container: Container) -> str:
    chat_id = str(client.post("/chats", json={}).json()["chatId"])
    seed_dataset(container.repos, container.blobs, chat_id=chat_id, user_id=DEV_USER, dataset_id="a2")
    return chat_id


def _submit(client: TestClient, chat_id: str, key: str) -> Any:
    content = FIXTURE_REQUEST.read_text(encoding="utf-8").strip()
    return client.post(f"/chats/{chat_id}/requests", json={"content": content, "artifactIds": ["a2"]},
                       headers={"Idempotency-Key": key})


def _events(client: TestClient, chat_id: str, mid: str) -> list[dict[str, Any]]:
    """The stream until the server closes it, each event's data decoded."""
    body = client.get(f"/chats/{chat_id}/requests/{mid}/events").text
    return [{"event": e["event"], "data": json.loads(e["data"])} for e in sse_events(body)]


def _unanswered(client: TestClient, chat_id: str) -> list[str]:
    items = client.get(f"/chats/{chat_id}/messages").json()["items"]
    answered = {m["inReplyToMessageId"] for m in items if m["kind"] == "clarification_response"}
    return [m["messageId"] for m in items if m["kind"] == "clarification" and m["messageId"] not in answered]


def _plan_calls(container: Container, mid: str) -> int:
    return len([c for c in container.repos.model_calls.list_by_request(mid) if c.stage == "plan"])


def test_submit_streams_to_a_report(tmp_path: Path) -> None:
    with api_client(tmp_path, model=_model(six_task_plan()), run_worker_in_api=True) as (client, container):
        chat_id = _chat(client, container)
        submitted = _submit(client, chat_id, "e2e-1")
        mid = submitted.json()["messageId"]
        events = _events(client, chat_id, mid)
        detail = client.get(f"/chats/{chat_id}/requests/{mid}").json()
        items = client.get(f"/chats/{chat_id}/messages").json()["items"]
    assert submitted.status_code == 202
    assert events[-1]["event"] == "request" and events[-1]["data"]["status"] == "COMPLETED"
    assert all("taskId" in e["data"] for e in events if e["event"] == "task")
    assert sorted(t["status"] for t in detail["tasks"]) == sorted(["COMPLETED"] * 4 + ["SKIPPED"] * 2)
    assert detail["usage"] == {"inputTokens": None, "outputTokens": None,
                               "estimatedCostUsd": None, "modelCalls": 4}
    report = next(m for m in items if m["kind"] == "report")
    assert report["requestMessageId"] == mid and report["report"]["claims"]
    assert all(c["evidenceRefs"] for c in report["report"]["claims"])


def test_two_clarifications_round_trip_through_replies(tmp_path: Path) -> None:
    model = _model(clarification("Which accounts are yours?"), clarification("Which months?"), six_task_plan())
    with api_client(tmp_path, model=model, run_worker_in_api=True) as (client, container):
        chat_id = _chat(client, container)
        mid = _submit(client, chat_id, "e2e-2").json()["messageId"]
        url = f"/chats/{chat_id}/requests/{mid}/replies"
        first_wait = _events(client, chat_id, mid)
        [first_q] = _unanswered(client, chat_id)
        answered = client.post(url, json={"inReplyToMessageId": first_q, "content": "ACC-SAV-1 and ACC-CUR-2"})
        second_wait = _events(client, chat_id, mid)
        [second_q] = _unanswered(client, chat_id)
        stale = client.post(url, json={"inReplyToMessageId": first_q, "content": "again"})
        decided = client.post(url, json={"inReplyToMessageId": second_q, "content": "x", "decision": "approve"})
        final = client.post(url, json={"inReplyToMessageId": second_q, "content": "September and October 2026"})
        done = _events(client, chat_id, mid)
        kinds = sorted(m["kind"] for m in client.get(f"/chats/{chat_id}/messages").json()["items"])
    assert first_wait[-1]["data"]["status"] == second_wait[-1]["data"]["status"] == "WAITING_USER"
    assert answered.status_code == final.status_code == 201
    assert stale.status_code == 409 and stale.json()["error"]["code"] == "not_pending"
    assert decided.status_code == 400 and done[-1]["data"]["status"] == "COMPLETED"
    assert kinds == sorted(["request", "clarification", "clarification", "clarification_response",
                            "clarification_response", "report"])
    assert _plan_calls(container, mid) == 3

## Deviations from the spec, decided in this plan

- `Last-Event-ID` is honoured (the brief asked for it; 11.5 says none): the event id is the newest `updatedAt` the stream has sent, and a reconnect skips records older than it. There is still no server-side replay store, and the client's E5 and E3 refetch remains the guaranteed path.
- When a stream opens on an open request it first sends the current Tasks, assistant Messages and request (11.5 describes only changes), which closes the gap between the client's refetch and the open. A request already closed at open still gets exactly one `request` event.
- WAITING_USER closes the stream only once the unanswered question is visible, because the worker writes the status before the Message.
- The `activity` event (11.1 expectation 15) is not built: it needs a worker-to-stream channel, and this phase's stream reads Messages and Tasks only. It can join as an in-process bus while API and worker share a process.
- On a reply the API claims WAITING_USER → RUNNING (as 11.4 says, though 11.3 says the worker owns every status but CANCELLED) and the worker continues with the new `RequestRunner.resume_claimed`; phase 1's `resume`, which claims for itself, stays for direct callers. The claim is what makes a double-clicked reply a 409.
- Paging slices whole repository lists in `core/services/paging.py`; phase 10 moves it into the repositories with `LastEvaluatedKey` behind the same `Page` type. E3 pages walk from newest to oldest, and each page reads oldest first.
- Phase 1's derived ids (clarification, report) are hash-based and do not sort by time, so E3's `messageId`-ordered pages can put them on a different page from their neighbours. The frontend reads one page of 100 and sorts by `createdAt`, so this is invisible today; a time-prefixed derived id is the fix.
- An archived chat behaves as not found on every chat-scoped route.
- E14 is GET only; PATCH /me arrives with phase 7. Dev login is a fixed user id from settings.
- Error code `internal` (500) is added for unexpected failures. FastAPI's request validation errors map to 400 `validation`, because 422 is reserved for `upload_mismatch`.
- Limits the spec does not set, chosen here: a title from the first request is at most 60 characters (the frontend mock's rule); a renamed title at most 200; request and reply content at most 10,000 characters; `limit` 1 to 100, default 50; `Idempotency-Key` at most 200 characters; the idempotency client key is `"{userId}:{chatId}:{Idempotency-Key}"`; a stream lives at most 900 seconds.
- An unexpected exception in a run marks the request FAILED with a generic reason. Phase 1 left it RUNNING for an operator requeue; the checkpoint is still kept, so a requeue is still possible.
- A replayed submit enqueues another start; the runner's conditional claim makes it a no-op instead of the API deduplicating the queue.
- Settings live in `api/settings.py`, not spec 12's `core/settings.py`, so phases 2 and 10 can add theirs without a conflict; they merge into one module after the wave.
- The worker loop module is `worker/consumer.py` (spec 12's name; the brief said `worker/main.py`). There is no separate worker process before phase 10, because in-memory repositories cannot be shared across processes.
- `Repositories.users` has an in-memory default so existing constructors keep working; phase 10 passes its DynamoDB users repository explicitly.
- `tests/helpers.make_deps` and `worker/deps.build_worker_deps` both assemble `WorkerDeps`; `make_deps` delegates once phases 2 and 3 have merged (a short change at merge time), so this plan keeps its `helpers.py` edits additive. New tools (phase 3's `read_artifact`) belong in `build_worker_deps`.
- `touch_chat` saves the whole Chat; when phase 7's worker starts writing `Chat.lastRequestStatus`, both writers need field-level updates to avoid lost updates.
- `default_model()` returns `ScriptedModel({})`, so until phase 2 replaces it a dev request ends FAILED with the planner's script-exhausted reason.
- Seam for phase 10: the dev stack's SQS queue (visibility 1200 s, dead letter after 3 receives) needs delete-after-handle, and `Queue` has no ack today. Phase 10 adds one (or a receipt on `WorkMessage`) and `QueueConsumer.handle` calls it after the runner returns, including after it marks a request FAILED. A resume delivered twice to two workers at once is deduplicated only by the checkpoint's pending interrupt; one consumer per message (the visibility timeout) keeps that safe.
