# AI cost engineering: what the evidence supports

Research date: **7 November 2026**. Scope: public evidence published in 2024–2026 about the cost of LLM applications, agents and retrieval systems. Audience: an engineering team building a web research agent.

[Read this report in Box](https://app.box.com/file/2576811318681).

This report was researched by Codex using public sources. It is a reference answer for ContextForge, not a report generated by the ContextForge engine. The existing Claude report in Box was read before research, so this is an informed replication and audit, not a blinded comparison. [Comparison with the Box report](../evals/ai-cost-box-comparison-2026-11-07.md).

## Executive summary

The strongest practical approach is to measure **cost per successful task**, then reduce repeated input and unnecessary work while checking that answer quality holds. The evidence supports cache-friendly context, selective tool-result handling, workload-specific model selection, and reuse of validated intermediate work. It does not support one universal savings percentage.

- **Production unit costs can fall without changing the model.** Uber reports lower request and session costs with a model held constant; this is stronger operational evidence than a token-price comparison, but still not an independently audited experiment. [Uber engineering](https://www.uber.com/us/en/blog/efficient-software-factory/)
- **Many impressive figures measure something narrower than money.** Manus describes a cached-input price ratio; Cursor measures generation speed and index reuse; Anthropic measures token use or retrieval failures. Their denominators must accompany their numbers. [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), [Cursor infrastructure case study](https://fireworks.ai/customers/cursor-fast-apply-speculative-decoding), [Anthropic retrieval experiment](https://www.anthropic.com/research/contextual-retrieval)
- **More agents can improve breadth at substantially higher token usage.** The architecture is justified when useful parallel work and better answers compensate for the extra cost. It is not a default cost optimization. [Anthropic research system](https://www.anthropic.com/research/multi-agent-research-system)
- **For ContextForge, the next investment is research quality.** A bounded search/read/verify/synthesize loop, traceable evidence, and a strong evaluation set take priority over adding PDF ingestion, vector storage, or more connectors. This is our design recommendation, not a published company result.

## How evidence is classified

**Company-reported measurement** means the company or an implementation partner publishes the result. **Benchmark** means a result on a specified evaluation, not a production guarantee. **Capability documentation** describes what a service offers, not what our application will save. **Inference** is an engineering conclusion drawn here. These labels establish provenance, not independent validation.

Sources were opened and the selected headline claims checked against their surrounding scope. Search snippets alone are insufficient for a final numerical claim. The review is bounded, not an exhaustive survey of every company or every assertion in the Box report. All links were accessed on the research date; rolling product documentation can change.

## Company case studies

### Uber: optimize the whole request path

Uber's August 27, 2026 engineering post reports approximately **34% lower cost per 1,000 model requests** from its peak and **52% lower cost per session** from the June peak, holding one model constant. Those are different baselines. The body and chart use different endpoint wording—February–July versus August—so the precise interval should remain qualified. The post describes model selection, context management and tool handling as complementary levers. It does not prove that total company expenditure or cost per successful task fell by 52%. [Original engineering post](https://www.uber.com/us/en/blog/efficient-software-factory/)

**Inference:** track request cost, session cost and successful-task cost separately. Keep comparable task cohorts when assessing an optimization.

### Manus: stable prefixes make repeated input cheaper

Manus's July 18, 2025 account describes an approximately **100:1 input/output token ratio** and a historical **10× cached/uncached input-price difference**. It recommends stable prompt prefixes, deterministic serialization and append-only context. The price ratio concerns one token category; the article does not establish a tenfold reduction in the whole agent bill or a production cache-hit percentage. Historical model prices are not current tariffs. [Manus context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

**Inference:** measure cache-eligible tokens, actual cache reads, writes and misses before predicting savings. Do not put volatile request metadata ahead of a reusable prefix.

### Cursor: specialize a predictable step and reuse preprocessing

Fireworks's June 23, 2024 participant case study reports Fast Apply at roughly **1,000 tokens/second**, approximately **13× vanilla Llama-3-70b throughput** and **9× the previous GPT-4 speculative-edits deployment**. This concerns applying edits, not the entire coding workflow or a published cost-per-edit saving. [Fast Apply case study](https://fireworks.ai/customers/cursor-fast-apply-speculative-decoding)

Cursor's January 27, 2026 indexing post describes Merkle trees, chunk embedding caches and teammate index reuse. Its **92% average repository-clone similarity** is not a 92% cost reduction. [Securely indexing large codebases](https://cursor.com/blog/secure-codebase-indexing)

**Inference:** avoid recomputing identical preprocessing, while retaining permission and content checks. Measure completed-work cost as well as speed.

### Intercom: task evaluations can change model selection

The July 30, 2025 OpenAI customer case study reports **20% lower evaluation cost for GPT-4.1 versus GPT-4o** and describes task reliability testing. It also says GPT-4.1 could handle work initially expected to need a reasoning-model stack. These are application-specific comparisons, not evidence that every Fin resolution costs 20% less. [Intercom customer case study](https://openai.com/index/intercom/)

Intercom documents a staged Fin retrieval/response pipeline, but that documentation does not quantify retrieval's financial contribution. Its April 2, 2026 Apex announcement claims improvements over frontier models without publishing sufficient numerical methodology to establish a universal advantage. [Fin AI Engine](https://intercom.help/fin4all/en/articles/10645579-the-fin-ai-engine), [Fin API announcement](https://www.intercom.com/blog/introducing-the-fin-api-platform)

**Inference:** maintain small, repeated application evaluations and distinguish historical deployments from newer specialization claims.

## Comparing the mechanisms

| Mechanism | What is actually reported | Evidence type and boundary |
|---|---|---|
| Selective tool loading | Anthropic labels the reduction **85%**; its rounded context counts are approximately 77K → 8.7K tokens | Internal example involving a large tool library; the rounded counts imply about 88.7%, so do not present both as an exact arithmetic identity |
| Programmatic tool calling | **43,588 → 27,297 tokens**, reported as **37% less** | Anthropic's complex-research evaluation; not a measured whole-company bill reduction |
| Code execution with MCP | **150,000 → 2,000 tokens**, approximately **98.7% less** | Illustrative discovery/loading example; not a typical saving for every data-transfer workflow |
| Context editing | **84% fewer tokens** | A **100-turn web-search evaluation**, not every short research request |
| Retrieval plus reranking | Failure rate **5.7% → 1.9%**, a relative reduction of about **67%** | Top-20 retrieval failures in Anthropic's tested setup, not 67% fewer hallucinations |
| Plan-template caching | Average cost **−50.31%**, latency **−27.28%**, retaining **96.61%** of the accuracy-optimal baseline | APC paper's evaluated workloads; retained relative performance is not absolute answer accuracy |
| Batch processing | **50% lower API cost**, with a **24-hour** completion window | OpenAI service capability for supported workloads; unsuitable for interactive steps that need an immediate result |

Sources: [advanced tool use](https://www.anthropic.com/research/advanced-tool-use), [code execution with MCP](https://www.anthropic.com/research/code-execution-with-mcp), [context editing](https://claude.com/resources/articles/context-management), [contextual retrieval](https://www.anthropic.com/research/contextual-retrieval), [APC paper, version 2](https://arxiv.org/html/2506.14852v2), [Batch API](https://developers.openai.com/api/docs/guides/batch).

These percentages must not be added or multiplied to predict an application's savings. The interventions overlap and use different workloads, denominators, models and baselines. The 85% label/count discrepancy is present in the publisher's example; reporting it accurately is preferable to silently repairing it.

## What this means for architecture

### 1. Treat context as a measured resource

Use a stable shared prefix and keep raw pages or large tool results behind artifact references. Supply the next step with the evidence it needs, not an ever-growing transcript. OpenAI's current prompt-caching documentation says cached-input discounts can reach **95%**, depending on the model, and that prefix matching is required. This is a capability ceiling rather than a promised application-wide saving. It also differs from older 90% guidance; dated reports should not be silently rewritten as though their original claim was fabricated. [Current prompt-caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching)

**Our recommendation:** compare total input, cached input, output, failed attempts, tool spend and answer quality on the same research cases. Provider-specific features and rates must be checked separately for the Bedrock models we actually use.

### 2. Choose parallelism according to the research question

Anthropic's June 13, 2025 report says its lead/worker system outperformed a single Opus 4 agent by **90.2% on its internal research evaluation**. It also reports multi-agent usage at roughly **15× chat tokens**, versus about **4× for an agent**. This is not 90.2% absolute accuracy or a 15× comparison against the single-agent baseline. [Research architecture and evaluation](https://www.anthropic.com/research/multi-agent-research-system)

Cognition's June 12, 2025 argument emphasizes shared context and the implicit decisions made by actions. It is a design argument about coordination risks, not a controlled disproof of all parallel research. [Cognition's context-engineering argument](https://cognition.com/blog/dont-build-multi-agents)

**Our recommendation:** parallelize independent read-only questions, consolidate evidence centrally, and reserve budget for resolving contradictions and writing the synthesis. Repeatedly searching the same query is not useful parallelism.

### 3. Reuse plans without reusing stale answers

APC stores and adapts plan templates rather than simply returning an old answer to a similar question. Its measured savings motivate an experiment, not a production guarantee. Fresh source retrieval is still needed when facts can change. [APC methods and results](https://arxiv.org/html/2506.14852v2)

**Our recommendation:** first cache stable execution structure and identical fetched content. Date, geography, permissions and source changes must invalidate reuse where they affect correctness. Do not return an old numerical answer merely because the wording is similar.

### 4. Retrieve better before expanding infrastructure

Anthropic's retrieval experiment contextualized chunks, combined lexical and semantic retrieval, and reranked candidates. It tested a final top-20 context; it does not establish that trimming to five chunks preserves the same quality. [Retrieval methodology](https://www.anthropic.com/research/contextual-retrieval)

**Our recommendation:** for today's public-web product, improve query selection, HTML extraction, evidence selection and source verification first. This finding does not make a vector database or PDF pipeline a prerequisite for good web research.

## A transparent cost calculation

Let **P** be the uncached input price per token, **rP** the cached-read price, **T** total input tokens, and **h** the fraction receiving cached-read pricing. Ignoring output and cache-write charges:

`input_cost = T × P × ((1 − h) + h × r)`

For an **illustrative assumption**, not an observed production result, use `h = 0.80` and `r = 0.10`. Input cost becomes `0.28 × T × P`: **72% lower input cost**. Whole-task savings will be smaller when output, writes, search and failures remain unchanged. They can be worse if a cheaper path lowers the completion rate.

Measure `cost_per_success = all_attempt_cost / successful_tasks`. Include failed and retried attempts in the numerator. Report the quality definition and success count beside this metric; an undefined success denominator can make a cheap but unreliable system look good.

## Recommended experiment for ContextForge

This is a proposed experiment, not completed engine validation:

1. Use the ten cases in [the web research benchmark](../../evals/cases/web-research-suite.md), with source-backed reference facts for the first case.
2. Hold the question, source access, cutoff, tool limit and report rubric constant when comparing models.
3. Enforce at most **50 combined search/fetch invocations per request**, shared across tasks, retries and resumes. Retain the separate spend cap; stop with explicit gaps if either limit is reached.
4. Grade claim support, numerical scope, question coverage, contradictory evidence, and clarity before optimizing cost. Page-count and report length are supporting observations, not quality scores.
5. Log model routes, tool attempts, source versions, cached input, output, latency and the estimated spend for every completed or failed attempt.
6. Compare one change at a time: query planning, result extraction, context selection, then model routing. A clean local test is needed to attribute any improvement.

## Limitations and unanswered questions

- Company and vendor results are self-reported. The review does not independently reproduce production experiments or verify underlying private data.
- We did not verify the Box report's every secondary-source claim, including the Intercom podcast savings, additional router papers or all hardware benchmarks. Unverified here does not mean false.
- The existing Box report is broader and includes interview preparation material omitted from this report. This report concentrates on evidence boundaries and ContextForge's immediate research workflow.
- Current documentation is a living source. Exact historical feature availability and every November 2026 price were not reconstructed.
- No public source establishes our agent's quality, savings, or absence of hallucinations. Those require engine runs, inspectable evidence and evaluation. Zero observed unsupported claims is a release criterion, not a guarantee of perfect factual correctness.
